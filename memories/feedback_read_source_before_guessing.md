---
name: Read source before guessing on orchestration internals
description: When a runtime, orchestrator, or library produces unexpected behavior, read the source — the function that owns the behavior, its callers, its defaults — before proposing or applying any fix.
type: feedback
volatility: durable
---
When a runtime layer (an orchestrator, a scheduler/dispatcher, library internals) produces unexpected behavior, do not propose a fix from inferred or hypothesized behavior. Read the actual source: the function that owns the path, its callers, and the default values it computes. This applies most strongly to non-user-facing paths — demand-probes, scaling, session lifecycle, hooks — where the documented contract is partial and the code is the ground truth.

**Why:** A worker pool once stayed empty despite a routed work item. The hypothesis offered was "the item is assigned and the orchestrator's default scale query only matches unassigned items," and a speculative `--assignee=""`-style change was applied before verifying. The pushback was direct: don't take a speculative action — do a deep dive into the docs and actual code and make an evaluation. Reading the configuration source confirmed the filter was literally an unassigned-only query, but only after the speculative step had already been taken — which clouded the diagnostic signal and could have masked a different underlying cause. The same investigation arc surfaced a second, completely separate failure (a pre-start hook exiting non-zero) whose cause was *not* what had been imagined: the runtime pre-creates the working directory with its own runtime files inside before the pre-start hook runs, and the "directory exists" check missed that case; a canonical reference script in the codebase had the correct stage-and-restore pattern. Both fixes were verifiable against source; either speculative path alone would have wasted time and produced unreliable knowledge.

**How to apply:** When a runtime layer's behavior surprises you, before making any change: (a) find the function that owns the behavior — `grep -rn` for the symbol, feature name, or error string in source; (b) read it together with its callers and defaults; (c) only then formulate a fix. Locate the load-bearing files first — the entry points, the configuration/defaults module that computes effective query and scaling values, the session-lifecycle code, and any canonical reference implementations in the codebase (adopt those patterns rather than reinventing them). Source-reading takes 5-15 minutes for typical paths; speculative fixes take longer when they're wrong.
